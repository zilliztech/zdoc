# REST reference pipeline

How the REST reference is produced: OpenAPI fragments, upstream drift, and
availability operations. The runbook and section index live in
[README.md](../README.md).

## Editing REST spec fragments

REST interfaces are generated from the OpenAPI fragments under
`packages/docs-tooling/src/reference/rest/meta/openapi/`. Treat a fragment
change as a source-and-contract change; do not hand-edit generated REST MDX,
Chinese REST sidebars, or Japanese REST translation files.

When adding an operation:

1. Add or update the operation in the correct fragment, including its HTTP
   method, path, tag, `summary`, request/response schemas, and localized
   `x-i18n` fields. Keep the fragment registered in
   `meta/fragment-migration.json` when it is part of the formal REST
   publication set.
2. For every operation generated for `zh-CN`, add the exact page title used by
   the Chinese generator as an entry to
   `packages/docs-tooling/src/reference/rest/meta/titles.json`. The value is
   the stable English slug without the automatic `-v2` suffix. For example,
   `创建 Spark 回填任务` maps to
   `create-spark-backfill-job`. Missing this entry fails Chinese REST
   generation before the site build.
3. Check whether the change affects lifecycle evidence, manifest inputs,
   generated sidebars, or translation ownership. These are derived outputs
   and must be regenerated by the supported tooling, not edited manually.
4. Run `pnpm test:for-change -- <changed-path>...` for every changed source,
   metadata, workflow, or test path. A selector failure means the code-to-test
   matrix is missing an entry and must be handled in the same PR.
5. Before submitting, run the selector's full command union,
   `pnpm test:rest-publication-contract`, `pnpm test:workflow-policy`, and
   `git diff --check`. Also run the Chinese REST generator in a temporary
   output directory and confirm the expected MDX filenames, titles, and slugs.

When deleting or renaming an operation, remove it from the source fragment and
update the corresponding fragment migration/lifecycle evidence and any
explicit navigation or manifest contract that refers to it. Verify the
generated diff contains the expected deletion or rename and no unrelated
generated files. A deleted generated page may also leave a translation input
or cache entry; let the reconciliation tooling classify and handle that
change rather than deleting translation files directly.

REST publication also produces one `generated/<locale>/manifests/rest-derivation.json`
for each generated locale. The English REST lane owns the `en` and `ja-JP`
manifests; the Chinese REST lane owns `zh-CN`. Each manifest binds the complete
OpenAPI fragment set by SHA-256 to the exact generator tooling commit, and the
Fetch validation, the atomic publication boundary, and `write-provenance.mjs`
at the end of every site build recheck those fragment hashes
(`REST_DERIVATION_FRAGMENT_DRIFT`). These files are dev-owned publication state
and must never be edited on `master`.

Because the fragments are master tooling while the generated pages and
manifests live on `dev`, the master-to-dev sync regenerates the whole REST
derivation set on its exact merge candidate
(`scripts/docs-workflow/regenerate-sync-candidate.js`, see
[the sync specification](../.claude/specs/2026-08-03-master-tooling-dev-sync.md)).
After a fragment PR merges, expect the resulting sync PR to carry the
regenerated REST pages, sidebars, and manifests, plus a child commit that
reconciles the Reference manifests and localization inventory when the pages
changed; the sync does not wait for the next Fetch. Fetch's REST lanes keep
publishing the same bytes on their schedule.

The English build runs both English and Japanese locales. A new REST operation
can therefore fail later, during `Validate and build generated docs`, if its
generated Japanese localization input is untracked or lacks valid candidate
provenance, even when English generation succeeded. The Chinese producer has a
separate `build:zh-CN` path and the Chinese `titles.json` check happens earlier,
but it must still pass its own validation and build stage after generation.

For a new interface, the minimum review checklist is: source operation and
`x-i18n`; Chinese title mapping; fragment/lifecycle/manifest contracts; test
matrix coverage; generated English/Chinese output; and the English build's
Japanese localization provenance.

## REST upstream drift watchdog and refresh

The REST fragments are kept aligned with their upstream specs through two
workflows driven by `packages/docs-tooling/src/reference/rest/meta/upstream/rest-upstream-lock.json`.
The lock pins one commit per upstream source: `zilliz-cloud-control-plane` (a
spec-file source) and `milvus-data-plane` (a source-tree source, classified by
the vendored Go extractor). See
[the pipeline design](../.claude/specs/2026-10-28-rest-upstream-pipeline-design.md),
[the 10-21 replay alignment report](../.claude/specs/2026-10-28-rest-upstream-replay-10-21-alignment.md)
(P1), and [the P2 milvus extractor report](../.claude/specs/2026-10-29-rest-upstream-milvus-extractor-p2.md)
for the acceptance evidence.

`rest-upstream-drift-watchdog.yml` runs daily and on demand. It is read-only:
for each source it compares the tracked ref HEAD with the pin and, on drift,
runs the deterministic diff at HEAD — spec-file sources download the upstream
spec, source-tree sources download the non-test Go files of the pinned
directory and extract the skeleton with the vendored extractor (the workflow
installs Go 1.27 via `actions/setup-go`; locally, `go` must be on PATH). The
report artifact (`rest-upstream-drift-<run_id>`) carries
`watchdog-report.{md,json}` plus the raw `diff.json`/`diff.md` (and the
extracted `skeleton.json`) per drifting source. The substantive headline
counts only drift a refresh run can resolve: description/summary drift is
deliberately excluded because the fragments keep their own text (prose stays
local), so it re-flags on every scan against an unchanged spec — it still
rides the diff report and the refresh PR's review lists. The report card is always
created and its finish status mirrors the drift result (`success` only when
no source drifts and no unmanaged release track exists); delivery is
best-effort and subject to `FEISHU_NOTIFICATIONS_DISABLED`. The lock file is
never written by the watchdog; pins move only through reviewed refresh PRs.

`rest-upstream-refresh.yml` is dispatched by an operator after a watchdog
report (inputs: `source`, optional `upstream_commit`, `base_ref`,
`draft_pr`, optional `lifecycle_track`). One dispatch produces one PR per
source (decisions-first pipeline, design
`.claude/specs/2026-10-29-rest-upstream-decisions-pipeline-design.md`):
prepare an isolated staging directory (diff plus touched fragment copies plus
the ruleset, with a repository-path isolation sweep), build the machine-generated
candidate list and take one model stance per candidate on the internal gateway
(`scripts/rest-upstream/decide-batches.js`, batched per fragment — plus a
synthetic `(operations)` bucket for upstream-added operations, which exist in
no fragment yet and owe the ledger a decision — with citation/contract gates
and a stance-coverage floor), plan scenario-tab placements for added and
unattributed fields (`scripts/rest-upstream/branch-plan.js`; the model picks
existing tab labels only), draft evidence-grounded descriptions for
prose-less added/mirrored nodes (`scripts/rest-upstream/describe-additions.js`)
and fill zh-CN/ja-JP for the new prose (`scripts/rest-upstream/translate-additions.js`;
a degraded entry is dropped whole — fail-closed — and listed in the PR),
assemble the change set deterministically from those stances
(`rest-upstream-assemble` — structure mirrors the resolved upstream subtree
with the fragment's prose and `x-*` preserved; the model never writes a path
or a value), and apply it with the deterministic applier (every entry must
bind to a cited diff entry; denylist, `x-*`, and oneOf branch structure are
asserted; schema nodes the fragment never had inherit the nearest managed
lifecycle triple so the release-track projections stay complete, while
subtrees pinned `x-include-target` without `milvus` never inherit), gate the
T4 ledger accounting, run the canonical bytes check, the change-scoped
`test:for-change` union plus `pnpm test:rest-publication-contract` and
`pnpm test:workflow-policy`, and `git diff --check` — no site builds (a
master checkout has no dev-owned `generated/`, so site verification happens
in the sync candidate build on the dev tree right after merge) — and finally
open the PR with
`REST_UPSTREAM_REFRESH_PAT` so the pull-request checks actually run. The same
commit bumps the lock pin to the refreshed upstream commit with its content
SHA (atomic adoption: the watchdog goes quiet exactly when the PR merges) and
lands ledger proposals as conservative `deferred` ledger entries so the PR
stays atomic; human review reclassifies them in the PR. For milvus
data-plane dispatches, pass `lifecycle_track` (e.g. `3.0.x`) to make the diff
derive `x-added-at`/`x-last-modified`/`x-deprecated-since` suggestions; the
applier binds lifecycle change-set values to those suggestions and requires an
explicit override to deviate. The refresh workflow handles source-tree sources
end to end (checkout-free GitHub contents fetch, `setup-go` 1.27, vendored
extractor).
The PR body embeds the diff report, the applier log (overrides, ledger
drafts, inherited lifecycle attributions, unaddressed entries), the
retirement/translation/description review lists, and the decision divergences
(explicit model skips with reasons plus every model output line the
citation/contract gates rejected) for human review. Pre-existing prose in all
three languages is preserved by the mirror; newly introduced prose lands with
zh-CN and ja-JP, and model-drafted English descriptions are grounded on
upstream evidence and fragment references. Retired-field reports include
constraint-only losses (an enum or bound dropped while the field survives) —
check the fragment-level diff before accepting them, and remember a container
rename reports every inner field as retired.

When a refresh run fails at a gate, its `rest-upstream-refresh-<run_id>`
artifact carries the whole staging directory plus the applied output — enough
to rehearse a fix locally instead of re-dispatching to discover the next
gate: re-run the applier on the run's `change-set-translated.json` against
`staging/fragments`, rebuild the lifecycle-evidence inventory over the
overlaid fragments (`scripts/rest-upstream/refresh-lifecycle-inventory.js`,
module API `{root, restMeta, appliedFile}`), and execute the same
change-scoped union the workflow runs (the command list is visible in the
failed run's step log). A full local pass means the next dispatch is verified
before it starts.

Required credentials and variables (all fail closed when missing):

- `REST_UPSTREAM_GITHUB_TOKEN` — contents:read on `zilliztech/zilliz-cloud`
  (falls back to `PRODUCT_DOC_LINKS_GITHUB_TOKEN`).
- `REST_UPSTREAM_REFRESH_PAT` — a PAT allowed to push a `rest-upstream-refresh/*`
  branch and open a PR; it must not be the default `GITHUB_TOKEN` (bot-PR CI
  is phantom by design).
- `AGENTIC_PROVIDER_API_KEY` plus `REST_UPSTREAM_AGENT_MODEL` and
  `REST_UPSTREAM_AGENT_BASE_URL` (each falls back to the translation agent's
  `AGENTIC_*` counterparts).

Upstream deltas are classified in the append-only ledger
(`meta/upstream/ledger.json`): `adopted`, `rejected`, `deferred`, or
`external`. Bootstrap (2026-10-28) pre-registered the 51 stock fragment-only
operations (v1 legacy, spark, access-control, api-keys, private-endpoint) as
`external` plus 3 deferred decisions. Generate or merge further classifications
with:

```bash
node packages/docs-tooling/src/reference/rest/index.js rest-upstream-ledger-bootstrap \
  --from-diff <diff.json> --date <YYYY-MM-DD> --out <proposal.json>   # review, then:
node packages/docs-tooling/src/reference/rest/index.js rest-upstream-ledger-bootstrap \
  --merge <proposal.json>
```

`rest-upstream-prepare` builds the same staging directory locally for manual
rehearsals (add `--allow-empty-drift` when no drift exists). The decision stage
(`scripts/rest-upstream/decide-batches.js`) reads only a diff output, so
rehearsing it locally needs no staging — just the same gateway credentials the
workflow injects (`AGENTIC_PROVIDER_API_KEY` or `DEEPSEEK_API_KEY` plus the
model and base URL vars), `--diff <diff.json>`, and an output path.

Source-tree sources (milvus) diff against an extracted skeleton instead of a
spec file. Produce one from a pinned checkout of the upstream directory and
pass it with `--skeleton`:

```bash
go run packages/docs-tooling/src/reference/rest/upstreamDiff/milvus/extractor.go \
  --dir <checkout>/internal/distributed/proxy/httpserver --out skeleton.json
node packages/docs-tooling/src/reference/rest/index.js rest-upstream-diff \
  --source milvus-data-plane --skeleton skeleton.json --out diff-out
```

The extractor reads the route table and request structs of the pinned Go
package and emits structural truth only (paths, handler names, request
fields, Go-level types, `binding:"required"` membership); prose, response
shapes, and doc-layer constraints are documentation territory and stay out of
the skeleton.

## REST upstream and availability operations

The daily cadence and the human touchpoints of the REST program. Design in
one line: the machine discovers, assembles, validates, and publishes; humans
decide timing, judgments, and commitments. See
`.claude/specs/2026-11-01-rest-availability-harness.md` (availability),
`.claude/specs/2026-11-01-zilliz-release-notes-survey.md` (zilliz tiers),
and `.claude/specs/2026-11-01-x-zilliz-cluster-types-proposal.md` (registry).

**Daily (passive).** The drift watchdog runs at 04:17 UTC over both pinned
sources and milvus tags. Green: nothing to do. Drift red: note the
substantive count, batch it until a refresh is worth one model run. Track
coverage red: a new milvus minor line exists — start the new-track sequence
below. If the card does not arrive, `gh workflow run
rest-upstream-drift-watchdog.yml` and read the `watchdog-report.md` artifact.

**Refresh (on demand, the only paid step).** When accumulated drift matters:

```bash
gh workflow run rest-upstream-refresh.yml \
  -f source=zilliz-cloud-control-plane \
  -f upstream_commit=<sha from the watchdog report> \
  -f base_ref=master -f draft_pr=true
```

The run assembles the change set deterministically and opens a draft PR.
Review only the judgment lists in the PR body: retirements (did the field
really die upstream), pendingConfirmation (required relaxations go back to
R&D), unplaced/reorganize (scenario-tab placement), translation degradations,
and ledger flips for new operations (drafts land as deferred). Merge moves
nothing else: the master-to-dev sync regenerates REST artifacts, byte-compares
them, and auto-merges when green.

**Milvus releases.** A new patch of a managed track (for example 3.0.6) has no
automatic reminder — the watchdog report lists `latestTag` per track as an
informational field. Re-run the availability matrix for that track and diff
verdicts; behavior flips become reviewed fragment updates:

```bash
# milvus-cell vCluster: helm standalone pinned to the tag (v3.0.x needs
# requests 1c/2Gi, limits 4c/8Gi — LimitRange defaults starve the all-in-one
# process — plus extraConfig.http.requestTimeoutMs=120000), then:
kubectl port-forward svc/milvus 19530:19530 &
node packages/docs-tooling/src/reference/rest/index.js rest-availability \
  --base http://127.0.0.1:19530 --label milvus-<tag> --out tmp/rest-availability
```

A new minor line (watchdog card red): attribute its content with
`x-added-at: <new>.x` (source-verified per tag), extend the evidence, add the
matrix environment, then refresh.

**Zilliz cadence (manual by design).** New zilliz release notes: read the
GA / Public Preview / Private Preview / ON REQUEST tiers and update
`x-beta` / `x-next-channel` marks plus the prior rules in
`packages/docs-tooling/src/reference/rest/availability/zillizPriors.js`
through a reviewed PR. Suspected data-plane generation changes (serverless
has run a 3.0-generation plane while fresh Dedicated clusters defaulted to
2.6.x): create a disposable cluster and run

```bash
node packages/docs-tooling/src/reference/rest/index.js rest-availability \
  --base <cluster connectAddress> --label zilliz-<env>-<type> --zilliz uat3|prod
```

(transport note: the zilliz gateway rejects Node's TLS fingerprint with 401,
the runner rides curl for `--zilliz`). New CU categories in
zilliz-cloud-config manifests: extend the `x-zilliz-cluster-types` domain in
CUSTOM_ATTRIBUTES §1.13 and its contract test. API keys are project-scoped
regardless of the owning user's role — cluster creation outside the key's
project fails with 96041; environment work means key scope first.
