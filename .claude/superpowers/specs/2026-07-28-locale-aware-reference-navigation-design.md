# Locale-Aware Reference Navigation and Chinese Content Completeness Design

**Date:** 2026-07-28  
**Status:** Approved in principle; awaiting written-spec review  
**Target repository:** `zdoc`  
**Target worktree:** `.claude/worktrees/unified-docs-clean-room`  
**Target branch:** `codex/unified-docs/01-foundation`

## Summary

Repair the English, Japanese, and Chinese documentation navigation without making the three sites share one content hierarchy.

The selected architecture introduces a locale-aware navigation core with site-specific adapters, publishes explicit per-SDK Chinese Reference sidebars, and rejects structurally incomplete Chinese SDK landing pages before they reach a site build.

The design preserves these existing product boundaries:

- English and Japanese are served as one product site. Japanese follows the English manual structure and may continue using Docusaurus locale support within that site.
- Chinese is a separate product site with an independently selected manual set and document hierarchy. It must not be remodeled as a Docusaurus translation locale of the English site.
- English Reference content remains canonical. Japanese and Chinese Reference content is produced by the existing Agent-driven translation workflows and checked into the repository before a site build.
- `zdoc_cn` is an archive/reference implementation only. This work does not publish changes to it or reintroduce repository synchronization.

## Problem Statement

Local Docker previews expose three related but distinct failures.

### Japanese Reference navigation loses context

`packages/docs-ui/src/en/theme/DocSidebar/index.tsx` identifies Reference sub-navigation with a regular expression rooted at `/reference/`. A Japanese path such as `/ja-JP/reference/python` therefore does not resolve to the Python Reference context.

When classification fails, the specialized two-level Reference navigation is skipped. The narrow/merged sidebar then collapses the visible tree to an incomplete overview. The same implementation also contains absolute `/docs/...` and `/reference/...` links that can send Japanese users to the English locale.

### Chinese Reference navigation combines unrelated SDKs

`packages/site-config/src/sidebars/zh-CN/reference.ts` currently assigns one autogenerated root sidebar to every Reference sidebar key. Opening the Python Reference can therefore expose Python, Java, Go, Node.js, REST, and CLI documents in one tree.

The tooling registry and publication tests already model locale-specific Chinese outputs such as `generated/zh-CN/sidebars/python.sidebar.js`, but the checked-in Chinese sidebar artifacts and overrides are absent and the site loader does not consume them.

### Chinese navigation renders through English assumptions

The shared Chinese `DocSidebar` entry point reuses an English implementation whose default Reference origin contains an English Guides primary rail and English absolute links. The UI implementation is shared, but its navigation data and route construction are not yet site-aware.

### Some Chinese Reference landing pages are placeholders

At least one Chinese SDK landing page contains only a short sentence and `<DocCardList />`, while the corresponding English and Japanese pages contain a complete SDK overview. Correcting the sidebar alone would make the page discoverable without making it complete.

## Goals

- Preserve the current visual design while restoring the expected top-level and two-level navigation behavior.
- Keep Japanese Reference navigation in the Japanese locale throughout navigation.
- Give each Chinese SDK and protocol an isolated Reference sidebar.
- Use the Chinese site's own Guides rail, labels, and capabilities around Chinese Reference content.
- Preserve English structure for Japanese Reference and per-SDK Reference structure for Chinese translations without forcing Chinese Guides to match English Guides.
- Publish Chinese Reference sidebars and content through the existing staged, Agent-driven tooling workflow.
- Fail before a site build when required sidebar artifacts, referenced documents, or Chinese SDK landing-page structure is incomplete.
- Verify the behavior through unit, configuration, build, Docker, and browser smoke tests.

## Non-goals

- Redesigning the header, logo, sidebar visual treatment, icons, or responsive layout.
- Converting Chinese into a Docusaurus locale of the English site.
- Requiring English and Chinese Guides to have identical manuals or hierarchy.
- Translating content during `pnpm build` or a Docker image build.
- Evaluating sentence-level translation quality in the structural validator.
- Replacing the current Agent translation system.
- Restoring or synchronizing changes into `zdoc_cn`.
- Refactoring unrelated documentation plugins or build optimizations.

## Alternatives Considered

### 1. Locale-aware shared navigation core with site adapters

This is the selected approach.

Shared code owns route parsing, Reference context selection, responsive sidebar state, and the two-level rendering behavior. A site adapter supplies the site-specific primary rail, labels, Reference targets, locale behavior, and route construction policy.

Benefits:

- fixes the root coupling rather than one route at a time;
- lets English and Japanese share a product structure while preserving the Japanese prefix;
- lets Chinese reuse the UI without importing English navigation data;
- keeps one implementation of sidebar interaction behavior;
- provides testable boundaries for route parsing and site configuration.

The cost is a focused extraction from the current English component, plus explicit adapter wiring for both site profiles.

### 2. Duplicate the complete sidebar implementation by site

An English/Japanese component and a Chinese component would make data isolation obvious and could be implemented quickly.

This was rejected because responsive behavior, Reference drill navigation, accessibility fixes, and future visual changes would need to be maintained twice. Japanese locale handling would still need to be solved inside the English copy.

### 3. Patch the path regular expression and Chinese sidebar loader only

This would make `/ja-JP/reference/...` recognizable and prevent the immediate all-SDK Chinese tree.

This was rejected as the final architecture because the shared component would retain English Guides data and locale-dropping links. It would pass a narrow test while preserving the coupling that caused the failure.

## Architecture

```text
current browser location
        |
        v
locale-aware route parser
  - locale
  - normalized pathname
  - manual
  - Reference target
        |
        +---------------------------+
        |                           |
        v                           v
shared sidebar state/rendering   active site adapter
                                - primary rail
                                - localized labels
                                - Reference targets
                                - route builder
                                - site capabilities
        |                           |
        +-------------+-------------+
                      v
          locale-preserving navigation
```

The shared renderer must not import English or Chinese content configuration directly. It receives all product-specific navigation through a typed adapter.

## Component Boundaries

### Route model

A small pure module owns route normalization and classification. Its input is a browser pathname plus the active locale configuration. Its output is a normalized route context.

Conceptually:

```ts
type DocsRouteContext = {
  locale: 'en' | 'ja-JP' | 'zh-CN';
  localePrefix: '' | '/ja-JP';
  pathname: string;
  normalizedPathname: string;
  manual: 'guides' | 'reference' | 'byoc' | 'onpremise' | 'unknown';
  referenceTarget?: 'python' | 'java' | 'go' | 'nodejs' | 'restful' | 'cli';
};
```

For the English/Japanese site, `/ja-JP` is removed only for internal classification. The route builder reapplies it to internal documentation links. For the Chinese site, the default locale has no locale prefix; site separation is selected by the build profile and deployment host, not by pretending Chinese is an English-site locale.

Aliases such as Reference document paths under `/reference/node/...` resolving to the `nodejs` target remain part of the Reference-target configuration rather than scattered conditional logic.

### Site navigation adapter

The adapter is immutable configuration consumed by the shared renderer. It defines:

- the primary Guides rail shown around Reference pages;
- localized rail and back-link labels;
- SDK/protocol display order;
- landing paths and accepted document-path aliases;
- Reference entry redirects such as CLI overview routing;
- whether a locale prefix must be preserved;
- capabilities that are intentionally absent from a site.

English and Japanese use the English product adapter. Japanese applies translated labels when available and the active `/ja-JP` prefix. Chinese uses a Chinese product adapter whose rail comes from Chinese Guides configuration. No adapter may silently fall back to another site's rail.

### Shared sidebar renderer

The existing sidebar interaction and responsive rendering stay shared. The following concerns move out of the English-specific implementation:

- pathname parsing;
- hard-coded Reference target lookup;
- hard-coded client-library links;
- hard-coded default Guides rail;
- site-specific back labels and entry redirects.

The renderer receives the active adapter and route context. It does not know how a site obtained its documents or sidebars.

## Reference Sidebar Publication

### Required sidebar keys

Both English and Chinese Reference loaders expose these explicit Docusaurus sidebar keys:

- `pythonSidebar`
- `javaSidebar`
- `nodeSidebar`
- `goSidebar`
- `restfulSidebar`
- `cliSidebar`

The Chinese loader follows the established English loader pattern. Each key loads only its corresponding generated artifact and applies only its corresponding Chinese override.

Expected Chinese publication outputs are:

```text
generated/zh-CN/sidebars/python.sidebar.js
generated/zh-CN/sidebars/java.sidebar.js
generated/zh-CN/sidebars/node.sidebar.js
generated/zh-CN/sidebars/go.sidebar.js
generated/zh-CN/sidebars/restful.sidebar.js
generated/zh-CN/sidebars/cli.sidebar.js
```

Expected optional, checked-in customization files are:

```text
sidebar-overrides/zh-CN/python.json
sidebar-overrides/zh-CN/java.json
sidebar-overrides/zh-CN/node.json
sidebar-overrides/zh-CN/go.json
sidebar-overrides/zh-CN/restful.json
sidebar-overrides/zh-CN/cli.json
```

An empty override is valid. A missing required generated sidebar is not valid for a release build.

### Structural relationship between locales

English is the structural source for SDK Reference manuals. Japanese translation follows the same English document IDs, hierarchy, and sidebar order because it is part of the English product site.

Chinese Reference translation also mirrors each English SDK's document hierarchy unless an explicit retirement or product exception exists. Chinese labels and page bodies are translated artifacts, not runtime imports from English.

The parity comparison operates within one SDK at a time. It must never compare the entire Chinese Reference filesystem to one English sidebar, because that would recreate the all-SDK coupling.

### Publication flow

```text
English Reference source
        |
        +--> English sidebar/content publication
        |
        +--> Agent translation job
                 |
                 v
          staged zh-CN content + sidebar
                 |
          structural/parity validation
                 |
          atomic publication to
          content/zh-CN/reference + generated/zh-CN/sidebars
```

The normal site and Docker builds consume checked-in publication outputs. They do not call Feishu, an Agent, or a translation service.

## Chinese Landing-Page Completeness

### Scope

The initial required set contains the entry/overview page for each translated SDK or protocol represented in the Chinese Reference rail. The validator is extensible, but this change does not attempt to score every API method page.

### Structural rules

A required Chinese landing page fails validation when any of the following is true:

- the expected page is absent;
- the matching sidebar does not reference it;
- its normalized prose is empty or below an explicitly configured minimum;
- its meaningful body consists only of imports, front matter, headings, or `<DocCardList />`;
- required structural markers derived from the source landing-page contract are absent;
- its document ID or route cannot be resolved by the site configuration;
- it contains internal documentation links whose checked-in targets do not exist.

The rules must be deterministic and configuration-backed. They must not call a language model during validation and must not use a subjective translation-quality score.

### Exceptions

Intentional Chinese product differences use an explicit, reviewed exception record containing:

- source document ID;
- Chinese disposition: translated, replaced, or retired;
- reason;
- replacement path when applicable.

Existing Reference retirement data should be reused where it expresses the same decision. The validator must not accept a broad wildcard that suppresses an entire SDK.

## Error Handling and Fail-Closed Behavior

Development helpers may produce a focused diagnostic explaining how to generate a missing artifact, but release validation and production builds fail when:

- a required per-SDK sidebar is missing or empty;
- one SDK sidebar references a different SDK's content tree;
- a sidebar document ID does not resolve;
- a required translated landing page is structurally incomplete;
- a Japanese internal navigation target loses `/ja-JP`;
- the Chinese Reference renderer receives the English Guides rail;
- a site adapter references a capability not declared by the active site profile.

There is no fallback to `autogenerated('.')`, the English rail, English page content, or another locale's generated sidebar.

Diagnostics identify the site, manual, SDK, artifact path, and failed invariant so Jenkins and GitHub Actions failures are actionable.

## Testing Strategy

### Unit tests

- Route normalization for `/reference/python`, `/ja-JP/reference/python`, nested Node.js aliases, trailing slashes, and non-Reference paths.
- Route building that retains `/ja-JP` for Guides, Reference landing pages, inner Reference pages, and back links.
- Adapter selection for English, Japanese, and Chinese site contexts.
- Manual Reference origin storage and clearing without cross-locale paths.

### Sidebar/configuration tests

- Every Chinese sidebar key loads one non-empty generated artifact.
- Python, Java, Node.js, Go, REST, and CLI sidebars are mutually isolated.
- Every sidebar document ID resolves under the active site's Reference content root.
- The Chinese adapter uses the Chinese Guides rail and localized labels.
- English and Japanese Reference structures remain aligned.

### Translation publication tests

- A staged Chinese Reference publication includes both content and the matching sidebar.
- Publication remains atomic when structural validation fails.
- Missing, empty, cross-SDK, and stale sidebars are rejected.
- Placeholder-only and undersized required landing pages are rejected.
- Explicit retirements and replacements are accepted only when their targets resolve.

### Build and browser tests

- Run the English default-locale static build.
- Run the Japanese locale static build as part of the English site.
- Run the Chinese site static build independently.
- Build and run the two production-style Docker images.
- Verify with Playwright that English, Japanese, and Chinese pages show the header, logo, primary rail, expected secondary navigation, and the correct SDK-only Reference tree.
- Verify Japanese clicks remain under `/ja-JP`.
- Verify representative Chinese Python, Java, REST, and CLI pages do not expose sibling SDK trees.

The browser checks assert structure and links, not pixel-perfect visual snapshots.

## CI and Deployment Integration

The new validators run before both GitHub Actions site builds and the corresponding `vdc-jenkins` image builds. They operate solely on the checked-out commit.

The change preserves the existing four deployment flows:

- English UAT
- English production
- Chinese UAT
- Chinese production

Production may continue either rebuilding from the selected commit or promoting a previously accepted UAT image. The navigation/content validation belongs to image creation; promotion reuses the already validated immutable image.

## Migration Sequence

1. Add failing route and locale-preservation tests around the current renderer.
2. Extract the route model and site adapter contract without changing visual output.
3. Wire the English/Japanese adapter and make Japanese Reference navigation locale-preserving.
4. Wire the Chinese adapter using the Chinese Guides rail.
5. Replace the Chinese autogenerated Reference placeholder with explicit per-SDK loaders.
6. Regenerate and check in the six Chinese sidebar artifacts through the existing publication workflow.
7. Add per-SDK sidebar isolation and resolution validation.
8. Regenerate incomplete Chinese SDK landing pages through the Agent translation workflow.
9. Add deterministic landing-page completeness validation.
10. Run static builds, Docker smoke tests, and Playwright acceptance checks for all three language views.

Each step must keep the English default-locale site buildable. Sidebar and content publication changes are committed atomically per manual or in a single verified translation publication batch.

## Acceptance Criteria

- `/ja-JP/reference/python` and representative nested Japanese Reference pages render the same navigation structure as their English counterparts with Japanese locale paths.
- Japanese navigation links do not unexpectedly resolve to default-locale English pages.
- Chinese Reference pages display the Chinese site's primary rail.
- Each Chinese Reference SDK/protocol page displays only its own generated sidebar tree.
- All six required Chinese Reference sidebars are checked in and validated.
- Required Chinese SDK landing pages contain complete translated overview structure rather than placeholder-only content.
- Missing or malformed navigation/content artifacts fail before a production site build.
- English, Japanese, and Chinese static builds pass.
- Both production-style Docker images contain only Nginx and the built static site at runtime and pass local browser smoke tests.
- No implementation or publication dependency on `zdoc_cn` is introduced.

## Compatibility Assessment

This change intentionally supersedes the former downstream-repository model. `zdoc_cn` remains useful as read-only historical evidence, but it is not a build input and receives no synchronized patch.

Compatibility validation therefore targets the merged repository's Chinese site profile and its Jenkins/GitHub Actions workflows. A discrepancy against the historical Chinese site is classified as intended product difference, corrected migration behavior, or regression before acceptance.
