# GA4 404 自动修复 PR2：定时调度 + 自动开 PR + ledger + 回复执行器（为 PR3 铺路）

## Context

PR1（#1156 已合并）落地了确定性分类工具与 triage 协议，但回路止步于 artifact：无人盯守（dispatch-only）、决定不持久（无 ledger）、修复靠人工拼 conf、triage 回复没有机器可读的通路。PR2 按已定案设计闭合这三段：**每日 schedule + PAT 自动开 PR（带 ledger 提交）+ issue_comment 结构化回复执行器**。PR3 的 codex 分诊/解释器将插入本 PR 定义的回复协议与执行通道。用户已拍板：**复用 `REST_UPSTREAM_REFRESH_PAT`**；**每日调度 + open-PR 闸**（不采用每周频控）。

## 设计

### 1. Workflow（`.github/workflows/ga4-404-remediation.yml`，单文件两 job）

触发器：`schedule`（cron `19 3 * * *`，全仓空闲分钟位）+ `workflow_dispatch`（保留 days 输入）+ `issue_comment`（`types: [created]`）。顶层 `permissions: contents: read` 保持（写能力全在 PAT，同 rest-upstream-refresh）。并发组 `ga4-404-remediation` 不变，天然串行排队。

**Job `remediation`**（`if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'`）：
- checkout@v5（`persist-credentials: false`）+ setup-node@v5 '22'，**去掉 pnpm install**（工具零依赖，分类不需要 node_modules）
- 凭据门不变；分类运行加 `--ledger scripts/redirects/ga4-404-remediation-ledger.json`（tracked ledger 作为输入，fixed/declined/denylist 路径出局）
- artifact 上传不变 + 追加：ledger 更新版放进 artifact
- **自动开 PR 步骤**（有 direct 规则时）：三重闸 = ① direct.length > 0；② `gh pr list --label ga4-404-remediation --state open` 为空（open-PR 闸，防刷屏）；③ PAT fail-closed 门（复刻 rest-upstream-refresh 的 `test -n "$PAT" || exit 1` 文案）
- 开 PR 机制（照 `rest-upstream-refresh.yml:493-698` 的 Gate 10 模式）：node 单行把 report.json 的 direct 规则转成 mapping 文件（`mappings=[{from,to}]`）→ 工具 `--mode apply`（**与人工路径同一代码路径**）产出 conf 块+合并 ledger → 新分支 `ga4-404-remediation/<date>-<shortsha>`、bot 身份 `zdoc ga4-404 bot`、PAT URL push → `GH_TOKEN=$PAT gh label create ga4-404-remediation ... || true` + `gh pr create --label ga4-404-remediation`（body=proposal.md，60k 字符截断预算）→ triage.md 有内容时 `gh pr comment --body-file triage.md`（PR 的首个分诊评论，操作员在此回复）。PR 由 PAT 作者打开 → pull_request checks 自动跑（幻影 CI 免疫，无需自 dispatch）
- 无 direct 规则 → 只落 artifact + step summary，明确 notice

**Job `apply_reply`**（`if: github.event_name == 'issue_comment'`，前 gate 步骤便宜快速）：
- 门禁（任一不满足 → notice 后 exit 0）：PR 带标签 `ga4-404-remediation` 且 head 分支前缀 `ga4-404-remediation/`（恰好一个 open PR，0→notice、>1→fail-closed）；commenter 在 **repo var `GA4_404_REMEDIATION_ALLOWLIST`**（逗号分隔登录名，未设→fail-closed notice）；评论体含回复协议块
- checkout PR head 分支 → 提取回复块写临时文件 → `node scripts/redirects/ga4-404-remediation.js --mode apply --reply-file <comment.md> --conf deploy/en/nginx.conf --snapshot ... --ledger scripts/redirects/ga4-404-remediation-ledger.json --output-dir tmp/apply` → rules.conf 非空则连同 ledger.json 一起 commit（ledger-only 决定也提交）→ PAT push 回 PR 分支 → **确认评论**（含应用结果；**确认评论不含回复标记 = 防循环断路器**）。apply 拒绝（契约/ledger 校验失败）→ 拒因贴评论后 exit 1
- 用 gh 把评论体取到文件（`gh api repos/.../issues/comments/<id> --jq .body`）

### 2. 回复协议（本 PR 定死，PR3 的 codex 只产出/翻译成它）

`scripts/redirects/reply.js`（新模块）：标记 `<!-- ga4-404-reply-data begin ... -->` / `<!-- ga4-404-reply-data end -->` 包一个 ```json fenced 块，schema 与 apply mapping 文件完全一致（`{schema_version:1, mappings:[{from,to,note?}], declined:[{from,note?}], denylist:[{from,note?}]}`）。解析器：提取→剥 fence→JSON.parse→schema 校验；多块取第一个；无标记→`{ok:false, reason:'no reply block'}`（执行器据此 no-op）。CLI 加 `--reply-file`（与 `--mapping` 互斥、与 GA4 输入互斥），内部走同一 `runApply`。triage.md 构建器追加“如何回复”节（含可复制粘贴的回复骨架），PR 上的操作员不用读源码。

### 3. Ledger（tracked，决定持久化）

新文件 `scripts/redirects/ga4-404-remediation-ledger.json`（初始 `{schema_version:1, entries:[]}`；precedent=rest upstream 的 ledger.json 放工具旁；自动被现有矩阵行 `scripts/redirects/**` 覆盖）。**ledger 未决闸进工具**：apply 模式校验 mapping 的每个 `from` 不在 ledger 中已有任何 status（`path already decided in the ledger (status X)`），防重决/防循环。自动 PR 与 executor 的 conf+ledger 提交都走生成器（单写手不变式不变）。

### 4. 有界并发探测（PR1 挂账 P2）

`pipeline.classify` 的逐候选探测改为小并发池（`mapLimit` 帮助函数，并发 5，结果按原候选顺序回填），消除“最坏情形超 20min timeout 且无 artifact”的尾巴；测试钉顺序稳定性与并发上限。

### 5. Policy 引擎 + 测试（同变更强制项，来自探索清单）

- `scripts/validate-workflow-policy.js:27-34`：`TOP_LEVEL_DIRECT_PUSH_JOBS` 加 `['ga4-404-remediation.yml', new Set(['remediation', 'apply_reply'])]`（两个 job 都含 `git push`）
- `scripts/validate-workflow-policy.test.js`：按 mkdtemp/cpSync/mutate 惯例加负向测试（移除 map 项 → 断言精确错误 `git push is forbidden outside the declared Git writer inventory`）
- `scripts/redirects/ga4-404-remediation-workflow.test.js`：重写 PR1 的 dispatch-only 钉（会全部失败）为 PR2 正向契约：三触发器、两 job、push job 名与 policy map 一致、PAT fail-closed 文案、分支命名、label、commit 形状（conf+ledger）、executor 门禁（allowlist var 名、确认评论无回复标记、open-PR 闸）
- `scripts/sdk-reference-workflow.test.js` 不动（工作流不出现字面 `pnpm docs-tooling`，删掉 pnpm install 后更不会）
- 矩阵行不变（ledger 在 `scripts/redirects/**` 内）；**spec 表该行的"dispatch-only / must never push"句子必须改写**；`runbook/analytics.md` 重写调度/自动 PR/回复协议/ledger 段

### 6. 新增测试

`scripts/redirects/reply.test.js`（解析正/负/防循环）；apply 的 ledger 未决闸测试；`--reply-file` 端到端（临时文件）；mapLimit 顺序/并发上限测试；workflow 契约重写 + policy 负向测试。

## 执行步骤

1. 主 checkout pull master → worktree `.claude/worktrees/ga4-404-remediation-pr2` + 分支 `feat/ga4-404-remediation-pr2`
2. `reply.js` 解析器 + CLI `--reply-file` + ledger 未决闸 + triage.md 回复说明（先纯函数层测试驱动）
3. `mapLimit` 并发探测改造 + 测试
4. tracked ledger 文件 + workflow 重写（schedule/两 job/PAT 闸/开 PR/executor）+ 契约测试重写
5. policy 引擎 map 项 + 负向测试 + spec 句子改写 + runbook 重写
6. `pnpm test:for-change -- <全部变更路径>` 取 union 跑全（含 `test:workflow-policy`、`test:workflow-matrix`、`test:replay:all`——matrix/spec 触 replay-infrastructure 区）+ typecheck + `git diff --check`
7. 开 master PR，派 code-reviewer 评审，修复后合并（沿用 PR1 流程）

1. 设 repo var `GA4_404_REMEDIATION_ALLOWLIST=AnthonyTsu1984`（gh api，用户凭据）
2. dispatch 一次（days=7）：预期重新挖出 PR1 验收的那条 direct 规则（Auth-loginlog-in 尚未修）→ 自动开出带标签的 remediation PR，**该 PR 的 pull_request checks 真实运行**（幻影 CI 实证）+ ledger 'fixed' 提交 + triage 评论在 PR 上
