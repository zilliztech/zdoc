# shared-docs 上游 PR variant 采纳机制（方案 B）

## Context

Milvus/Zilliz 文档趋势同步发布，原"上游先合、zdoc 后跟"的时间差假设消失。11-11 用户拍板：未合并上游 PR 的内容以 **Zilliz 自有内容（variant）** 身份进入 next 通道；上游合并后内容身份转变为"共享内容"（re-pin 到 merge commit）。方案 A（lock v2 PR-pin）放弃——其"PR pin 仅 next 权限"无法覆盖"上游合并晚于 Zilliz 发布"的场景，且需要 refs/pull 抓取层×3、LOCK 语义重构、PR head 漂移 fail-closed 等大改造面；方案 B 对 lock/验证/git 获取层**零改动**（lock 永远只钉 on-branch commit），未合并内容只在采纳时刻抓取一次。

已拍板口径：**采纳范围=按需**（仅发布需要的 PR 走 adopt）；**对账=watchdog 报告 + 人工 #1151 式对账**（不做自动对账 bot）。

已核实的插入点：`read-page.ts:41-48`（唯一 variant 内容来源口）、`build-page.ts:353-354/482-484`（通道可用性 + merged.unchanged fast-path）、`shared-docs-validate.yml`（对 zdoc PR 树全量生成，variant 文件自动覆盖，零 workflow 改动）、`source-state.ts:129-130` + `guides-shared-sources.js:115` + `guides-shared-regeneration.js:124`（receipt 诚实化的 contained 改动）。

## 设计：variant 覆盖文件

页面目录新增 `shared-docs/guides/pages/<page>/variants/`：
- `next.md` — 喂 NEXT 通道 variant（可单独存在 = UAT 预览态）
- `current.md` — 喂 CURRENT 通道 variant（**必须伴随 next.md**，校验规则）
- `<channel>.provenance.json` — `{pull, head_sha, adopted_via, adopted_at}`，head_sha 40-hex，必须存在

规则：文件字节 = 上游 PR 源文件**逐字节原文**（不改写；适配照常发生在构建期）；pins 校验逻辑完全不动（`isOnBranch`/`LOCK_ORDER` 照旧）；lock.yaml/source.yaml schema 不变。

生命周期：
1. **采纳**：`shared-docs adopt-variant --pull N` 抓一次 `refs/pull/N/head` → 写 variants/next.md + sidecar → master PR（评审闸）→ validate workflow 自动全量生成 → 合并 → sync → dispatch Fetch → UAT 显示（块级 `<NextChannel>` gating，Base 记录保持 CURRENT）
2. **上游先合并**：删 variants + re-pin 到 merge commit（#1151 式人工 PR，watchdog 附 diff 预览）→ 内容经 current 进生产
3. **Zilliz 先发布**：`--promote` 补 current.md（同字节）→ merged.unchanged → 生产按 current 输出自有内容；上游后合并时同 2 对账（保留的 zdoc delta 转 transform 或回馈上游）
