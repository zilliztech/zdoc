# 让 master→dev sync 在候选树上重生成 REST 派生产物

## 结论

你的判断成立：片段是 master tooling，sync 候选树里已经带了新片段，却拿 dev 的陈旧 `rest-derivation.json` 去对账，必然 drift。修法不是放松校验，而是把 Fetch 里 REST lane 的"生成→校验→原子发布"原样搬到 sync 的 **"Generate and verify candidate-derived files"** 步骤里：候选树 = dev 状态 + master tooling + **在该树上用 master tooling 重生成的 REST 产物**。drift 校验保持 fail-closed 不动，sync 不再依赖下一轮 Fetch。

历史佐证：2026-09-17（#655）与 2026-10-20（#783）两次片段变更都落进过"合并后、Fetch 前"的 drift 窗口；设计文档 `2026-09-04-publication-evidence-chains-unification-design.md:117` 当时把清单生成硬绑在"sync 之后的 REST publication"，从未考虑过候选树重生成——不是刻意否决，是当初 candidate-derived 只覆盖了 inventory 一个文件。

## 设计

### 1. 候选树 REST 重生成（复用 Fetch 的 REST lane，保证字节一致）

`_fetch-content-group.yml:158-182` 的 REST 发布就是三条 CLI 加一次对账，无需飞书/S3/网络（`rest/index.js` 纯本地确定性生成，`--upload-s3` 不传）。候选树本身已含 dev 精确状态，所以 Fetch 里的 worktree/`restore-generated-state`/workspace 预处理都不需要。sync 新步骤按顺序执行：

```
pnpm docs-tooling publish-group --site en    --group rest --stage fetch|validate|publish   # en 页 + ja 页 + en/ja 清单 + en sidebar
pnpm docs-tooling publish-group --site zh-CN --group rest --stage fetch|validate|publish   # zh 页 + zh 清单 + zh sidebar
pnpm docs-tooling reference-manifest --source content/en/reference --target content/zh-CN/reference --source-commit "$DEV_SHA" --write
pnpm generate:localization-input-inventory && pnpm check:localization-input-inventory      # 原有，必须在 REST 之后（inventory 覆盖 i18n/ja-JP 与 en sidebars）
```

`reference-manifest --write` 必须跟上：site validation 在 build 前跑 `validate-reference --site en|zh-CN`，它按文件哈希校验 `generated/en/manifests/reference.json` / `generated/zh-CN/manifests/reference-translations.json`，REST 页一变就必须同步重算（Fetch 的 zh lane 正是这么做的）。

`validate` 阶段会在候选树上用**新片段**复核**新清单**，正好把今天出错的那条检查变成通过证据。

### 2. 契约语义：candidate-derived 允许嵌套在 dev-owned 根下

`scripts/docs-workflow/master-tooling-sync.js:88-95` 现在要求 candidate-derived 与 dev-owned/master-authoritative 两两不相交，而 REST 产物全在 `content/`、`i18n/`、`generated/` 三个 dev-owned 根下。改为：

- **允许嵌套于 dev-owned 根**；`isDevOwned()` 对这些路径**仍返回 true**——`inspect`（master 历史不得碰 dev-owned）和 site validation 的 `ownership-gate` 行为完全不变，master PR 依旧不能手改 REST 产物。
- `isCandidateDerived()` 从精确匹配改为前缀匹配（目录项需要），且 **master-authoritative 优先**：en REST 输出目录里的 4 个 preserved 文件（`restful.md`/`versioning.md`/两份 error-codes）仍必须与 master 逐字节一致，重生成若碰坏它们 `verify` 直接拒。校验规则调整为：candidate-derived 路径不得位于 master-authoritative 路径**之下**，但可以**包含**它。
- `verifySyncCandidate()` 的"候选不得改 dev-owned"检查排除 candidate-derived；"候选在 dev-owned 之外必须等于 master"检查已排除 candidate-derived，保留。
- 白名单 `SUPPORTED_CANDIDATE_DERIVED_PATHS` 扩成完整集合，但契约校验从"**等于**白名单"放宽为"**是白名单子集**"。这是迁移必需：`bootstrap` 步骤用**新脚本**读 **dev 上旧契约**（只有 inventory 一项），等于规则会让首个携带本改动的 sync 在 bootstrap 就挂掉；完整集合由 `master-tooling-sync-workflow.test.mjs` 对契约内容断言兜底。

契约 `deploy/contracts/master-tooling-sync.json` 的 `candidateDerivedPaths` 扩为 11 项：原 inventory + `content/en/reference/api/restful/restful` + `content/zh-CN/reference/api/restful/restful` + `i18n/ja-JP/docusaurus-plugin-content-docs-reference/current/api/restful/restful` + `generated/{en,zh-CN}/sidebars/restful.sidebar.js` + `generated/{en,ja-JP,zh-CN}/manifests/rest-derivation.json` + `generated/en/manifests/reference.json` + `generated/zh-CN/manifests/reference-translations.json`。

### 3. 把派生步骤收成一个脚本

新建 `scripts/docs-workflow/regenerate-sync-candidate.js`（读契约驱动，`node:test` 可注入命令做 hermetic 测试）：按 §1 顺序执行 → `git add -A -- <全部 candidate-derived 路径>`（现有 `git diff --name-only` **漏掉未跟踪的新文件**，新增 REST 操作生成的新页会被漏加，必须用 `add -A` + `status --porcelain` 为空的检查）→ 断言工作树改动 ⊆ candidate-derived（任何越界路径 fail-closed）→ `git commit --amend --no-edit` → 输出 `candidate_sha`。workflow 步骤只保留 `pnpm install --frozen-lockfile` + 调用脚本 + 原有 `verify`。

### 4. `toolingSha` 显式传入

`packages/docs-tooling/src/cli.ts:1416-1423` 用 `git rev-parse HEAD` 当 toolingSha；在 sync 里 HEAD 是**稍后会被 amend 掉的**合并提交，清单会指向一个不可达 SHA。加一个可选环境变量 `ZDOC_REST_TOOLING_SHA`（必须 40 位 hex，格式不对即报错，不静默回退），sync 传 `TOOLING_SHA`，Fetch 不设则行为不变。

### 5. 触发策略：每次 sync 都重生成

不做"仅片段变了才生成"的条件判断：生成是确定性的，输入不变则页面零 diff，只有三份清单的 `toolingSha/generatedAt` 变化（Fetch 每 8 小时本就如此）；生成器代码变更也能顺带流到 dev，并顺手自愈任何原因导致的清单陈旧。代价是每次 sync 多约 1-3 分钟和一次清单 churn。Fetch 的 REST lane 保持不变，仍是正式发布者；sync 落地后下一轮 Fetch 会生成相同字节，不冲突。

## 实施中必须确认的两点

1. `publish-group --site zh-CN --group rest` 脱离 Fetch 时是否要求 `DOCS_TOOLING_ALIYUN_VALIDATOR_PROVIDER`（zh 适配器加载）；REST 页无图应为空跑，若必须则只设 provider 路径不设密钥。同时确认 `prepare-content-group-workspace.js` 对 rest 组是否必要。
2. `reference-manifest --write` 在只有 REST 页变化时是否会动其他 zh sidebar；若会，那些路径也要进契约或改为只写清单。
