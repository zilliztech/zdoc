# スケーリングのための Canary Upgrade アプローチ

Zilliz Cloud は、スケーリング操作に **canary upgrade** アプローチを使用します。プラットフォームはまず限定された範囲でターゲット構成を検証し、その後、ヘルスチェックに合格したら段階的にロールアウトします。

Query CU を増減したり、レプリカを変更したりすると、Zilliz Cloud は新しい構成の準備と検証が行われている間、クラスターを `Modifying` 状態にします。目的は、問題を早期に検出し、各ロールアウトステップで影響を受ける範囲を限定することで、サービスへの影響を軽減することです。

## Canary upgrade が重要な理由\{#why-canary-upgrade-matters}

Canary upgrade は、変更を広範囲に適用する前に、プラットフォームがターゲットリソースの健全性を検証する必要があるスケーリング変更向けに設計されています。

- Query CU の増加または減少

- レプリカの増加または減少

- 手動、スケジュール、または動的スケーリングによるサービス提供リソースの調整

| 利点 | 説明 |
| --- | --- |
| 初期の影響範囲が小さい | 新しい構成はまず限定された範囲に導入されるため、変更が拡大される前に潜在的な問題を検出できます。 |
| ヘルスチェックに基づくロールアウト | Zilliz Cloud は次のロールアウトステップに進む前に、準備状況とサービス提供の健全性を確認します。 |
| 段階的なトラフィック移行 | canary ステージが健全であることを確認した後、トラフィックは徐々に移行されるため、急激なキャパシティやレイテンシーの変動が起きる可能性を低減します。 |
| ロールバック経路 | canary が検証に合格しない場合、Zilliz Cloud はロールアウトを停止し、以前の利用可能な構成を引き続き使用できます。 |

## 仕組み\{#how-it-works}

![ITCnb4yRSoNlvgxb5cGcLjNInig](https://zdoc-images.s3.us-west-2.amazonaws.com/itcnb4yrsonlvgxb5cgcljninig.png "ITCnb4yRSoNlvgxb5cGcLjNInig")

canary upgrade を使用するスケーリング操作は、通常、次のシーケンスに従います。

| ステージ | 実行される内容 |
| --- | --- |
| 以前の構成 | スケーリングジョブの開始中も、以前の利用可能な構成が引き続きサービスを提供します。 |
| ターゲット準備 | Zilliz Cloud は、ターゲットの Query CU またはレプリカ構成を準備します。 |
| 限定的な canary | プラットフォームはまず限定された範囲で新しいリソースを検証します。 |
| ヘルスゲート | チェックが失敗した場合、ロールアウトは停止し、クラスターは以前の利用可能な構成を引き続き使用します。 |
| 段階的ロールアウト | チェックに合格すると、Zilliz Cloud は制御されたステップでロールアウトを拡大し、スケーリングジョブが完了するまで進めます。 |

1. **以前の構成を利用可能な状態に保つ**
スケーリングジョブの開始中、クラスターは以前の利用可能な構成で引き続きサービスを提供します。この期間中、クラスターは `Modifying` 状態になることがあります。

1. **ターゲット構成を準備する**
Zilliz Cloud は、ターゲットの Query CU またはレプリカ構成に必要なリソースをプロビジョニングして準備します。

1. **限定的な canary を実行する**
プラットフォームはまず限定された範囲で新しいリソースを検証します。canary ステージでは、新しいリソースが必要なデータをロードし、サービス提供状態を復元し、準備状況とヘルスチェックに合格できるかどうかを確認します。

1. **canary の健全性を監視する**
Zilliz Cloud は、canary の準備状況、サービス提供の健全性、移行動作を監視します。canary が期待される健全性基準を満たさない場合、ロールアウトは続行されません。

1. **変更を段階的にロールアウトする**
canary が健全であることを確認した後、Zilliz Cloud は制御されたステップでロールアウトを拡大し、ターゲット構成へサービス提供トラフィックを移行します。

1. **スケーリングジョブを完了する**
ターゲット構成が完全にアクティブかつ健全になると、スケーリングジョブが完了します。不要になったリソースは、サービス提供経路から外れた後にクリーンアップされます。

## Canary upgrade とクラウドネイティブストレージ\{#canary-upgrade-and-cloud-native-storage}

クラウドネイティブストレージは、永続データがコンピュートリソースから分離されているため、canary ベースのスケーリングをより安全にします。

多くの従来のステートフルシステムでは、新しいノードを追加するには、既存のノードがローカルデータを新しいノードに再配置する必要があります。その間、既存のノードはオンライントラフィックを処理しながら同時にデータも転送しなければならず、CPU、メモリ、ディスク I/O、ネットワークの負荷が高まる可能性があります。

Zilliz Cloud では、永続データはオブジェクトストレージに保存されます。新しいリソースは、サービス提供トラフィックに参加する前に、必要なデータを独立してロードできます。これにより、canary ステージは、既存のサービス提供ノードをローカルデータ転送元として依存することなく、新しいリソースを検証できます。

## スケーリング中に気付く可能性があること\{#what-you-may-notice-during-scaling}

canary upgrade ベースのスケーリング操作中は、次のようなことが起こる可能性があります。

- クラスターのステータスが `Modifying` に変わることがあります。

- canary の準備と検証が行われている間も、通常、既存のサービスは以前の利用可能な構成で継続して実行されます。

- 一部の管理操作が一時的に利用できなくなることがあります。

- ロールアウトステージ間でトラフィックが移行される際に、わずかなサービスの揺らぎが発生する場合があります。

- 新しい構成は、スケーリングジョブが正常に完了した後にのみ有効になります。

- canary またはそれ以降のロールアウトステージを正常に完了できない場合、クラスターは以前の利用可能な構成を引き続き使用します。

- スケーリングジョブ中、Zilliz Cloud は引き続き以前の構成に基づいてクラスターに課金します。新しい Query CU またはレプリカ構成が課金に使用されるのは、スケーリングジョブが正常に完了した後のみです。

<Admonition type="info" icon="📘" title="注意">

Canary upgrade はスケーリング中のサービスへの影響を軽減しますが、すべての操作で完全に揺らぎがないことを保証するものではありません。レイテンシーに敏感な本番ワークロードでは、可能であればトラフィックの少ない時間帯に大規模なスケーリング変更を実施してください。

</Admonition>
