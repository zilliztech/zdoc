# オンデマンドクラスターの監視

Zilliz Cloud コンソールを使用して、オンデマンドクラスターのアクティビティを監視し、個々のリクエストを調査して、コンピュート実行に関連するリクエストを確認します。これらのビューは、リソースの準備に費やされた時間と、リクエストの処理に費やされた時間を区別するのに役立ちます。

## クラスターのアクティビティを表示する\{#view-cluster-activity}

![VpjfwSufrhMjnpbRM9LccQYKngc](https://zdoc-images.s3.us-west-2.amazonaws.com/VpjfwSufrhMjnpbRM9LccQYKngc.png)

<Procedures>

1. Zilliz Cloud コンソールで、オンデマンドクラスターを含むプロジェクトを開きます。

1. **On-Demand Compute > クラスター** に移動し、調査するクラスターを選択します。

1. 期間を選択し、クラスターのアクティビティチャートとサマリーを確認します。

</Procedures>

アクティビティビューには、リクエスト量と結果、リクエストレイテンシ、コンピュートとコレクションの準備状態、および CU アクティビティが表示されます。これらのメトリクスを経時的に比較し、ワークロードまたは準備状態の変化を特定します。定義と計算の詳細については、[Metrics Reference](/docs/metrics-alerts-reference) を参照してください。

パーセンタイルは、観測された所要時間の分布を要約したものです。たとえば、P50 は、観測値の約 50% がその値以下になる値です。P95 は、約 95% の観測値がその値以下になる値です。パーセンタイルを解釈する際は、特に起動頻度の低いクラスターでは、サンプル数を確認してください。パーセンタイル値はヒストグラムから推定されるため、加算、減算、または平均化して別のパーセンタイルを求めることはできません。

## リクエストを調査する\{#inspect-a-request}

リクエスト履歴には、記録された Search、HybridSearch、および Query リクエストが表示されます。リクエスト履歴を使用して、リクエストを特定し、どこに時間を費やしたかを調査できます。

![N9qmwYpQFhuBhkbAT8Kc2HHDnmc](https://zdoc-images.s3.us-west-2.amazonaws.com/N9qmwYpQFhuBhkbAT8Kc2HHDnmc.png)

<Procedures>

1. クラスターのリクエスト履歴で、期間を選択します。時間フィルターはリクエストの開始時刻に適用されます。

1. 必要に応じて、操作、結果、または最小所要時間でリストを絞り込みます。

1. リクエストを選択すると、結果、合計所要時間、フェーズごとの所要時間、および関連する実行（利用可能な場合）が表示されます。

</Procedures>

リクエストは、進行中、成功、失敗、タイムアウト、キャンセル、または不明の状態になります。結果が不明とは、最終的な結果を確認できなかったことを意味します。失敗したリクエストについては、エラーコードが利用できる場合があります。

リクエストの所要時間は、Coordinator がリクエストを受信した時点から測定されます。クライアント側のネットワーク時間やゲートウェイ時間は含まれません。そのため、アプリケーションで測定した所要時間は、コンソールに表示される所要時間と異なる場合があります。

### リクエストのフェーズを理解する\{#understand-request-phases}

| フェーズ | 測定内容 |
| --- | --- |
| Prepare | リクエストの準備に必要なその他の処理です。 |
| Compute | このリクエストがコンピュートリソースの準備完了を待機する時間です。 |
| Load | このリクエストが、対象コレクションがクエリ可能になるのを待機する時間です。 |
| Queue | スケジュールされ、キューから取り出されるまで待機する時間です。 |
| Execute | キューから取り出された後のリクエスト処理です。前処理と後処理を含みます。 |

必要なリソースがすでに準備完了している場合、リクエストはフェーズをスキップすることがあります。リトライにより、リクエストが同じフェーズに複数回入る場合があります。表示されるフェーズの所要時間は、そのフェーズで費やされた時間を累積したものです。フェーズ値が欠落していることと、測定された所要時間がゼロであることは異なります。実行経路によってはフェーズが重複する場合があるため、すべてのフェーズの所要時間の合計が全体の所要時間になると想定しないでください。

**Compute** フェーズは、選択したリクエストが待機した時間です。コンピュートのアクティベーションがすでに開始された後にリクエストが到着した場合、その待機時間はアクティベーション全体の所要時間より短くなります。複数のリクエストが同じアクティベーションを待機する場合があります。

リクエストレベルの **Execute** フェーズは、キューから取り出された後に開始します。その境界は、トップレベルの実行試行を累積し、スケジューリングと内部リトライを含む集計実行時間メトリクスとは異なります。どちらも、純粋な QueryNode のコンピュート時間として解釈しないでください。

## 実行を調査する\{#inspect-a-run}

実行は、1 回のコンピュートアクティベーションに関連するリクエストをグループ化します。コンピュートが起動されたときに開始し、そのコンピュートが停止したときに終了します。実行ビューには、コンピュートの状態、観測された開始時刻と停止時刻、および関連する記録済みリクエストの結果別件数が表示されます。

![AwvAwHtaBh2NSCbwdYZcXKvlnPD](https://zdoc-images.s3.us-west-2.amazonaws.com/AwvAwHtaBh2NSCbwdYZcXKvlnPD.png)

<Procedures>

1. クラスターの実行リストを開き、期間を選択します。

1. 実行を選択して、その詳細と関連するリクエストを調査します。利用可能な場合は、リクエストに関連付けられた実行をたどることもできます。

1. 実行の準備完了時間とリクエストの結果を、リクエストの詳細と比較します。

</Procedures>

リクエストは、実際に入った、または待機した最初の実行に関連付けられます。別の実行に到達した内部リトライは、実行間のリトライとしてマークされ、元のリクエストの実行統計では再度カウントされません。信頼できる実行との関連付けがないリクエストは、実行のリクエスト数に含まれません。事前ウォームアップによって作成された実行には、関連するリクエストがない場合があります。

実行の件数は、記録された関連リクエストを反映しています。請求の数値ではありません。請求セッション ID は請求期間を識別するもので、実行 ID とは異なります。請求の詳細については、[On-Demand Compute Cost](/docs/on-demand-compute-cost) を参照してください。

## 準備状態と欠落データを解釈する\{#interpret-readiness-and-missing-data}

**コンピュートの準備状態**は、アクティベーションの開始から、QueryNode が準備完了してリソースグループに参加するまでを測定したものです。**コレクションの準備状態**は、アクティベーションの開始から、特定のコレクションがクエリ可能になるまでを測定したもので、コンピュートの起動時間を含みます。1 回のアクティベーションで複数のコレクション準備状態サンプルが生成される場合があります。コレクションがクエリ可能であることは、そのキャッシュがウォームであることを必ずしも意味しません。

リクエストレコードは非同期に書き込まれ、遅延または不完全になる場合があります。レコードが利用できない、または不完全とマークされている場合、空のリストまたはゼロの件数を、リクエストが発生しなかった証拠として解釈しないでください。進行中のリクエストは、リストを確認している間に状態が変わる場合があります。記録が開始される前に拒否されたリクエストは、リクエスト履歴に含まれません。
